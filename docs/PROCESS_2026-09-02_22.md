# torch.compile 一致性缺陷挖掘：从原始计划到现在的全过程（2026-09-02 ～ 09-22）

面向导师的过程梳理。按阶段记录：当时的假设是什么、做了什么工具、跑了多大规模、结果如何、为什么转向。只写挖掘本身。

## 0. 起点：原始研究计划（09-02）

《面向 Toxic Compilation 一致性缺陷的自动检测》把问题定义为：同一 Python 程序在 eager 与 `torch.compile` 两条路径下必须一致；不一致的根源在 Python 层的语义因素（张量元数据、Python 标量/开关、形状与下标的关联、别名与原地修改、缓存/特化上下文）。方法分四个阶段：

1. **Python 层语义分析**：识别编译边界，建轻量 IR，抽取语义因子与"测试义务"（哪些因子会改变程序语义、需要在两侧比较）。
2. **一致性导向的测试生成与差分执行**：单因子变异、边界引导、缓存/特化序列（A→B→A）、上下文切换；多层执行（Dynamo / AOTAutograd / Inductor）以定位缺陷所在层。
3. **七个一致性判据**：值、元数据、异常、原地修改、别名、梯度、缓存；失败最小化。
4. **面向开发者的报告**：自动收集环境、最小复现、触发条件、去重。

评估设计为 RQ1–RQ5（检测有效性、与 TorchProbe/NNSmith 等基线比较、静态分析贡献、缓存/特化检测、真实缺陷发现）。09-06 出了 v2 计划；09-07 起有两套并行实现（`harness/` 与 `plan/tcc`），后决定以 `plan/tcc` 为主线。

## 1. 第一阶段（09-07 ～ 09-11）：按计划实现工具，在受控基准上验证

计划的每一章都落成了模块：编译边界识别（在 torch 自带代码上验证：`_inductor/runtime` 51 个 `@triton.jit` 边界）、IR 与依赖切片、因子抽取、语义上下文签名、YAML 测试义务、种子（签名构造、OpInfo 官方样本、记录调用）、执行矩阵（冷/热缓存、A→B→A）、多层定位、七个判据、最小化、报告生成与去重。

**受控基准**：本机只有一个 torch 版本，无法用历史 buggy/fixed 对；改为向编译栈注入 19 个人工缺陷作为 ground truth（代码生成偏差 13、JIT 特化 4、缓存一致性 2）。结果：

- RQ1：19/19 检出，真实编译器上 0 误报，平均 4.19 个测试检出。
- RQ3 消融：从纯动态随机（7/19、338 个测试、109 个无效测试）逐层加静态分析到完整（19/19、235 个测试、16 个无效），检出单调上升、测试数下降；静态分析开销约 30 ms/程序。
- RQ4：缓存/特化类缺陷只有 warm 序列能触发；`compile.dynamic` 不能作 warm 切换因子。
- RQ2：NNSmith 接入作基线。

**真实缺陷（RQ5）第一次尝试是失败的**：单算子 OpInfo（约 700 算子，1,700 余程序）、轻量别名结构变异、多算子逐元素链、`module_db`、NNSmith 模型——两套实现在 2.14.0 CPU 上都只找到一个真缺陷（`var_mean` 空张量的 mean 为 0）。结论写在当时的记录里：这一层已经被 PyTorch 自己的 CI 覆盖，再挖不出东西。

同期做了两件铺路的事：**从 GitHub 挖 533 个历史 issue 复现程序**做语料（2.14.0 上 open 的 23/63 复现）；**Kaggle 自动化**（脚本生成 → 推送 → 轮询 → 取回），用于 Linux/gcc 与 Tesla T4 复核——之后每条结论都要过这一关。

## 2. 转向（09-11 ～ 09-13）：从"生成更多程序"到"看真实缺陷长什么样"

把 335 个真实 issue 标题分类后发现：缺陷密度最高的三块——**索引类算子、非法输入的静默接受（eager 拒绝、compile 照算）、算子间 dtype 转换**——恰好是生成器的空白；而预算花得最多的三块（浮点 dtype 阶梯、requires_grad、编译开关）在真实 issue 里占比很低。于是把"换输入"改成"换判据、换角度"，每个角度做成一个几分钟到几小时的扫描：

| 角度 | 规模 | 产出 |
|---|---|---|
| 分解 vs 核函数差分（不编译，秒级） | 553/558 算子 | 已知族 |
| 变形关系（配置开关 × 算子） | 593 算子 × 20 配置 | 0 违例：冷门开关不改单算子输出 |
| dtype 提升矩阵 | 全算子 | **高产**：`ldexp` 双向 dtype 错、`huber_loss`/BCE 混合精度返回 float32、`lerp(bool)`、`sum/prod(dtype=bool)` 编译失败——全在 Inductor lowering 层 |
| 复数变体 × 反向 | 全算子 | 复数 `pinv` / `matrix_sqrth` 梯度错（当时归因到 AOTAutograd；09-22 被更正，见 §5） |
| **Dynamo 的 Python 语义差分** | 151 个程序，30 秒 | **最高产**：`random.shuffle` 每次同一排列、`random.seed` 首调用被忽略、f-string 格式码、Python 3.14 namedtuple 递归、`str(KeyError)` 少引号——Dynamo 层缺陷密度远高于 Inductor |
| 优化器差分 | 1,584 配置 | 只 1 条（SGD foreach 复数） |
| 一元算子 × dtype × autocast × `out=` | 全算子 | 3 条，都属"eager 接受/拒绝 vs compile 相反" |
| 前向模式 AD 经编译 | 507 算子 | 数值 0 分歧，但 `ldexp` 进程崩溃、`quantile`/`addr` 断言两条新 |
| vmap 经编译 | 678 算子 | 0 |
| 0/1 特化 + 运行环境翻转 | 260 项 | 0 |

到 09-13 累计 27 条经过 2.14 + nightly + Linux 独立复核的候选，构成第一轮报告（09-15）。此时的认识：**Dynamo 的 Python 语义、非法输入的静默接受、dtype 边角 是三条主矿脉；单算子合法输入的数值一致性已饱和。**

## 3. 第四、五轮（09-20）：换判据

论文初稿（main.pdf，09-20）成稿后，提出两批角度并执行：

- **错误一致性**：用 OpInfo 的 `error_inputs`（226 算子）加约 70 条手写越界/形状错误，比较两侧是否同样报错——787 例，4 条"eager 报错、Inductor 静默返回"。
- **整数与类型转换的 C++ 未定义行为边界**：浮点→整数越界转换、整数溢出、移位越界等，长向量同时打到向量主体与标量尾部。
- **布局/别名矩阵**：534 算子 × 7 种布局 × 前向+反向，527 完全一致；发现 **池化反向按连续内存读取非连续 indices**（后成为第二轮里维护者反应最快的一条）。
- **NumPy-in-Dynamo**：`torch._numpy` 与真 NumPy 的差分（`np.fix`、`np.cbrt`、`np.clip(int8)`、`np.sign(nan)` 错值；int8 cumsum 溢出、`np.median` 形状、uint 算术报错等 dtype/形状分歧）。
- **跨目标**：同一 NumPy 程序语料喂给 Numba 与 JAX——Numba `remainder(INT_MIN, -1)` 进程崩溃；JAX `gcd/lcm(INT_MIN)` 死循环（维护者确认并指出 NumPy 有同样问题）。这证明方法不依赖 PyTorch。

## 4. 第六轮（09-21）：从"这两天什么最出货"反推——转到"实现路径"

| 方向 | 假设 | 规模 | 结果 |
|---|---|---|---|
| 图改写的前提 | 编译器的代数改写是否改变边界语义 | 183 例 | `x + 0` 作图输出时**返回输入本身**（别名泄漏；`joint_graph` 的消除没有 `post_grad` 那一套别名检查）；`x**-0.5`、cast 链 |
| 前缀一致性 | 同一元素结果是否随张量长度变化 | 135 例 | 1 ULP 级；负结果 |
| **C++ 工具链层** | Inductor 生成的 C++ 用 SIMD 内建函数，编译器优化器本身可能误编译 | 内建函数组合词表 v1–v3，最多 124,334 组合，MSVC / GCC / Clang | **MSVC x64 三个误编译**：`abs(abs(x))` 折叠、`x + 0.0` 向量加法被删、比较 + blendv 折成 min/max；GCC、Clang 干净 |
| 主机端 -O2 vs -Od | 178 批 | 只有上面的 `abs(abs)` |
| 模型手术 | 编译后改超参/优化器状态 | 76 例 | 命中"变化的 Python float 被烤进缓存图"的一角 |
| 符号整数算术 | `x.shape[0]` 派生的 Python 运算在追踪期折叠 | 138 表达式 × 3 后端 | `SymInt.__round__` 忽略负 ndigits；NaN 自比较被折叠；`(-1) ** n` 恒为 -1；整数 `div(rounding_mode="trunc")` 除零杀死进程 |
| 符号形状下标 | 112 程序 | 111 一致；`F.pad` 负 pad 超过输入时不报错 |
| **标量实参序列** | 同一编译函数连续用不同 float 实参调用 | 100 程序，每例独立缓存目录 | **18 个算子从第三个取值起沿用第二次的值**（norm eps、huber delta、SDPA scale、`interpolate(scale_factor)` 错形状……）；2×2 缓存开关矩阵证明 AOTAutogradCache 的键漏掉了派生表达式的特化守卫 |
| FX 代码生成 | 生成源码与 Interpreter 语义 | 手工探针 | `operator.pow(-2, x)` 打印成 `-2 ** x` |
| CPU 向量化 | 向量路径 vs 标量路径 | 手写 | 向量化 `remainder` 对 inf 除数得 NaN、结果依赖张量长度；int8/uint8 `min/max/argmin` ≥16 元素时补零通道参与归约 |

当天收工时的总结成为后面的指导原则：**缺陷集中在"同一语义有两条实现路径、只有一条被测试覆盖"的地方。**

## 5. 第七、八轮（09-22）：把"两条路径"系统化

### 5.1 上午

| 方向 | 规模 | 结果 |
|---|---|---|
| FX Interpreter vs 生成源码（把 pow 优先级推广） | 10,518 张图 × 四路执行（Interpreter / forward / deepcopy / pickle） | 三族真缺陷：pow 优先级；**形参名 `nan`/`inf` 遮蔽同名浮点常量**；**pickle / torch.save 往返把原地运算变成非原地**（反序列化重新符号追踪源码，`Proxy` 没有 `__iadd__`）——Dynamo 捕获的 `buf += g` 图存盘后缓冲区不再更新 |
| 特化值不在缓存键里（其它入口） | 56 程序 | **由 float 派生的 int 实参同样沿用旧值**（cumsum 维度、round 位数、linspace 步数……）；接受 SymInt 的位置与按值分支的分解全部正确 |
| 成对 lowering 静态审计（标量 vs 向量后端） | 全部同名方法并排 | 无新不对称 |
| Python wrapper vs C++ wrapper | 174 程序 + 138 表达式 | 171/174 一致；负结果 |

### 5.2 中午：全算子边界值扫描

对 OpInfo 全部约 530 个算子，把每个样本输入换成该 dtype 的边界值序列（0、-0.0、±1、±inf、NaN、±max、tiny、eps、2²⁴+1……），比较 eager 与编译；自包含脚本，可在本机（MSVC）、Kaggle Linux（gcc）、T4（Triton）上跑，被整数除零杀死或 CUDA 断言污染时自动重启续跑。规模约 **8,600 对 (算子, dtype)**，覆盖 f16/bf16/f32/f64/int8/uint8/int16/int32/int64/bool/complex64。

分诊：差异绝大多数归入三个已知族（低精度融合链中间量不按 float16 舍入、符号零、inf/NaN 边界上的算法/结合律差异）；扫描"重新发现"了第一轮已报的两个缺陷（`var_mean` 空张量、BCE 校验丢失）——覆盖率可信的证据。新命中：

- float16 融合链里 `y = x*x` 返回 inf 而同一次调用返回的 `isinf(y)` 是 False；`emulate_precision_casts=True` 在 CPU 与 T4 上都能修（与该问题原帖里机器人"开关无效"的结论相反）。
- **`torch.any(uint8)` 在 Inductor 下返回 bool**，eager、`aot_eager`、`torch.all` 都保留 uint8：`_refs.any` 的分解特意恢复 uint8，Inductor 给 `aten.any` 单独注册的 lowering 绕过了它，`aten.all` 没有 lowering 所以走分解。
- complex64 组里 `linalg.polar` 一行差异 → 下午的主线（§5.4）。

### 5.3 其它目标与反向

| 方向 | 规模 | 结果 |
|---|---|---|
| ONNX Runtime 优化开/关 | 154 程序 | 两级完全一致；负结果 |
| Numba `fastmath` / `parallel` | 268 程序 × 2 | fastmath 全在契约内；parallel 吞掉自身抛出的 ZeroDivisionError（2021 起已知） |
| 专门 lowering 绕过分解里的特判 | 1,726 个重载静态枚举 → 106 用例 | 新一族"dtype 未实现"校验丢失：`round(int, decimals)`（还返回 float32）、`ceil/floor/round(bool)`、`glu(int8)`、`adaptive_max_pool2d(int8)`；`F.pad` 越界填充值回绕 |
| **反向扫描**（OpInfo × 边界值 × 反向） | 508 对 | **`avg_pool1d/2d` 反向在 `ceil_mode=True` 时除数错**：越界的最后一个窗口按整核大小除，eager 按裁剪窗口除；前向一致；CPU 与 T4、2.14 与 nightly 都复现；定位到 `avg_pool2d_backward` lowering 的一个分支。GoogLeNet/Inception 式 `AvgPool2d(3, 2, ceil_mode=True)` 训练直接受影响 |

### 5.4 一条完整的追踪：从一行扫描差异到分发器缺陷

1. **起点**：Linux 上 complex64 组报告 `linalg.polar` 的 `P` 与 eager 相差 1.03。本机复现：`P` 非对角元虚部全为 0，`U @ P ≠ A`。
2. **换后端**：eager 后端正确，`aot_eager` 已错 → 不是 Inductor 代码生成。
3. **看图**：AOT 的图只有一个 `aten.linalg_polar` fallback 节点；把图直接调用是对的，只有经运行时包装器调用才错 → 问题在运行时上下文。
4. **逐项排除上下文**：no_grad、inference_mode、视图跟踪开关、各分发键的排除守卫……只有排除 **Conjugate** 分发键能复现同样的错值。
5. **找谁动了分发状态**：包装器内线程局部分发键集合多了 Python / PythonTLSSnapshot——运行时处在一个 `TorchDispatchMode` 之下。
6. **最小化**：一个只做 `return func(*args)` 的转发 mode，纯 eager 就能复现；同一公式逐算子写出、在同一 mode 下是对的 → 缺陷在 C++ 组合内核内部：`.mH()` 的惰性共轭视图被 `matmul` 消费时没有物化。
7. **刻画错值**：pinv 的错结果恰等于 `vh.mT @ diag(1/s) @ u.mH`（`vh` 少一次共轭）；polar 的 `P` 变成 `(X + Xᵀ)/2`。
8. **圈定范围**：51 个复数线性代数组合调用 → 整个 `torch.linalg` → 全部 OpInfo 算子 × 7 种 dtype（2,529 对）跑"eager vs 转发 mode"：只有 `pinv`/`pinverse`、`polar`、`matrix_sqrth`。
9. **回溯旧结论**：第一轮曾把"复数 pinv 梯度在编译下错"归因于 AOTAutograd 追踪反向公式（§2）。转发 mode 下的 eager 梯度与编译梯度**逐位相同**；只让前向在 mode 下跑、反向在外面跑，同样错 → 反向公式无辜，是保存的前向输出错了。旧归因据此更正。
10. **跨平台**：Linux CPU 同；T4 上 polar 同错、pinv 正确（cuSOLVER 路径不走同一内部公式）。

副产物是一个新的差分维度：**"eager 上下文 vs 编译运行时上下文"**——不需要编译器，几分钟扫完全部算子。

## 7. 认识的演变

- **09-11**："单算子 + 合法输入 + 数值一致性"已被 PyTorch 自己的 CI 覆盖；要看真实缺陷的分布来决定测什么。
- **09-13**：Dynamo 的 Python 语义、非法输入的静默接受、dtype 边角是三条主矿脉；Dynamo 层缺陷密度远高于 Inductor。
- **09-20**：换判据（异常一致性、UB 边界、布局、NumPy 语义）比换输入更有效；方法可以移到 Numba/JAX。
- **09-21**：真缺陷集中在"同一语义两条实现路径、只有一条被测试覆盖"处——Interpreter vs 生成源码、张量化 vs 特化、专门 lowering vs 分解、向量主体 vs 标量尾部、前向 lowering vs 反向 lowering、eager 上下文 vs 编译运行时上下文；两条都成熟的路径（两套 wrapper、ORT 优化级别、Numba parallel/fastmath）差分为零。
- **09-22**：扫描要能"重新发现"已知缺陷才可信；一行差异值得追到底（`polar` 追出分发器层缺陷并纠正了旧归因）；负结果划定了 torch.compile 的可靠层，是检测器裁剪扫描空间的依据。
