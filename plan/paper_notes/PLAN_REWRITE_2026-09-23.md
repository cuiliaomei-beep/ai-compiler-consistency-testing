## 1. 现状诊断

现稿（09-20 版）的主线是"从 Python 源码静态推导语义因子（SCS），一次变一个因子生成测试，分层 oracle 定位"。它有两个问题。

第一，故事与证据脱节。稿子的核心论证是"源码告诉我们该变什么"，但 09-20 以后的 46 项发现里，靠这条线找到的很少。真正高产的是另外三件事：把 OpInfo 算子放到边界值上（13、21、28–30、34–37、39 等）；对同一份 Dynamo 语料改变"怎么编译"（插 graph break、换 dispatch 上下文、换制品路径），同一批 274 个程序此前三轮差分只出已知分歧，换一个编译关系一轮就出两条新缺陷（40、41），再补一批按机制定向的程序又出一条（42）；以及把参照从 eager 换成高精度真值（39 的 erf/atanh 在 eager 与 compile 比较下几乎看不出来）。这些结果现在在稿子里只是"九个 factor-family analyzers"和 RQ5 的一句话，没有进入论点。

第二，数字与归因不实。稿子写 27 报告 / 11 确认 / 9 修复；`ISSUE_OUTCOMES.md` 今天的证据是 73 项（新 issue 55、评论 15、厂商反馈 3），维护者已修复 2、人工确认 9、独立复现或有修复 PR 13，其余尚无人工回应。73 项里约 10 项根因在 eager 内核、fx 层或运行时，5 项在 MSVC / Numba / JAX。全部算成"编译器一致性缺陷"经不起追问。

## 2. 新的主线

### 2.1 问题

`torch.compile` 让"同一份源码"对应多个制品：后端不同、graph break 落点不同、缓存冷热不同、dtype 与设备不同、导出与打包路径不同。一致性失效藏在两类因子的交点上：程序自身很少用到的语义（不支持的 dtype、近奇点输入、生成器协议、有序容器的重排），与编译流水线很少走到的路径（graph break 后的恢复函数、dispatch mode 下的复合算子、AOTI 的加载与销毁）。现有生成器（NNSmith、NeuRI、TorchProbe、FreeFuzz 等）几乎只在"程序"这一个轴上取样，把编译路径当作固定黑箱，因此既到不了这些交点，出了差异也说不出是哪一层引入的。

### 2.2 观察

两个因子空间都可以从现成材料里廉价地枚举，不需要生成新程序。程序侧的因子来自源码（现稿的 SCS）和算子元数据（OpInfo 的 dtype 支持表、样本形状）；路径侧的因子来自流水线本身的结构（可插 graph break 的语句位置、可替换的后端与模式、可切换的 dispatch 上下文、可往返的制品格式）。在其中一个轴上固定、另一个轴上一次改一个因子，就得到既可归因又高产的测试。这个观察把现稿的"一次变一个因子"从输入扩展到编译路径，是新稿区别于所有差分测试工作的地方。

### 2.3 方法（写法上仍是四部分，内容重排）

0. 蜕变测试只作解释、不作框架（用户 09-23 决定：主线用 OUTLINE_B，“编译路径作为测试维度”；方法节里用一到两段说明每个路径因子在形式上是一个语义保持变换、oracle 是一致性关系，并引用 Chen et al. / Segura et al.）。下面这段原先的框架化写法保留作参考，不再采用：整个方法写成蜕变测试：源测试用例是程序 P 在 eager 下的一次执行；后续测试用例是同一程序在一个语义保持的变换 T 下、沿另一条执行路径 B 的执行；蜕变关系是"可观察量相等"（数值在容差内相等、dtype / 形状 / stride 相等、异常类型相同且被同一 handler 接住、副作用相同、对象身份关系相同）。程序侧因子（边界值替换、dtype 替换）和路径侧因子（graph break 插入、后端替换、dispatch 上下文、制品往返）都是生成后续用例的变换，区别只在改的是输入还是编译方式。这样写有两点好处：不需要为编译器行为写显式规约（oracle 问题由关系本身解决），并且能和 TorchProbe（语义保持的程序变换）、EMI / Le et al.（编译器的等价修改）、AlignGuard（冷热缓存）在同一框架下比较——它们各用了这个框架的一个变换族。方法节先给这个框架（一段加一张"变换 × 可观察量"的表），再分别讲因子来源、oracle 和归因。引用 Chen et al. 的蜕变测试综述与 Segura et al. 的 survey 作为出处。
1. 因子来源。程序侧：源码静态分析得到 SCS（保留现稿 Phase 1，篇幅压缩）；算子侧：OpInfo 元数据加边界值表。路径侧：一组"编译上下文蜕变关系"——语句级 graph break 插入、后端分层（Dynamo-only / aot_eager / inductor）、执行上下文（TorchDispatchMode、autocast、dynamic、cudagraphs）、制品往返（export save/load、AOTI 打包、runner 生命周期）。关系的语义都是恒等，因此任何差异都是缺陷。
2. Oracle。一个固定的比较器，比七类可观察量：数值（float64 或多精度参照）、dtype / 形状 / stride、别名与对象身份、异常类型与是否被 handler 接住、副作用与外部状态、进程级结果。要点是把"参照"和"可观察量"都写成明确的选择，并用 39（erf）、40（副作用）、41（身份）、42（异常）、43（进程崩溃）说明每多一类可观察量就多一族原本看不见的缺陷。
3. 归因。分层执行给出差异进入的层（保留现稿 Phase 3），再加一条"根因在流水线之外"的出口：差分把 eager 内核、fx 层、编译器后端（MSVC）的缺陷也照出来，论文把它们单列而不并入主统计。
4. 报告。现稿 Phase 4，缩为一段。

### 2.4 论证要用的证据

- 一条关系胜过三轮程序（40、41、42 的来龙去脉）：同一语料、同一 oracle，只换编译关系。这是"路径轴被忽视"最直接的证据。
- 边界值 × 元数据一轮出一族（36：134 个算子 / 418 对在 eager 拒绝的 dtype 上照算；37 在 CUDA 上再出 73 对）：说明"程序侧因子可以从元数据枚举，不必生成程序"。
- 参照强度（39、34、35）：eager 与 compile 相互比较看不到的精度损失，多精度参照一次全出。
- 可观察量强度（41 身份、42 异常、43 崩溃）：每类各一条代表。
- 负结果（编译组合律、autocast、HOP、自定义算子、export 往返数值、CI 容差清单）：界定失效不出现的地方，同时说明关系并非越多越好。
- 维护者反应按用户定的四档给出（已修复 = 已合入或已有开发者提交修复 PR；已确认 = 维护者口头确认或有人复现；Pending；拒绝；为 0 的档不列），数据只来自 `ISSUE_OUTCOMES.md` 的"论文口径"表；三类归因分开统计。

### 2.5 研究问题（替换现稿 RQ1–RQ5）

- RQ1 两个因子轴各自的贡献：固定程序集，只加路径关系，找到多少新差异；固定关系，只加程序侧因子，找到多少。用现有 jsonl 直接算，不需要新实验。
- RQ2 oracle 的每一类可观察量各贡献多少发现；去掉多精度参照会漏掉哪些。
- RQ3 归因：分层执行把多少差异定位到了单一层；定位结果与维护者最终修在哪一层是否一致（已修复与已有 PR 的项可以核对）。
- RQ4 与现有生成器比较：保留现稿的注入缺陷基准与 Random / NNSmith 对照，但结论改写为"程序轴生成器在路径轴上的覆盖为零"。
- RQ5 真实缺陷：73 项、分类、维护者反应、修复情况，含负结果。

### 2.6 预计会被攻击的点与回应

- "这只是差分测试。" 回应：差分是 oracle，不是贡献；贡献是把编译路径当作可枚举的因子空间，以及关系集合本身。相关工作里最接近的是 TorchProbe 和 AlignGuard（冷热缓存），两者都只在一个维度上做。
- "很多发现不是编译器缺陷。" 回应：主统计只算严格的一致性失效（约 31 + 第一轮的大部分），其余两类单列，并说明差分 oracle 天然会照出参照方的缺陷。
- "工具与方法不对应。" 回应：论文只承诺方法与数据可复现；提供统一入口和每条发现的复现脚本，探针实现的历史形态不影响结论。
