# 论证提纲 B：不以蜕变测试为框架（2026-09-23）

与 OUTLINE_2026-09-23.md（方案 A）对照。两份提纲的证据相同，差别在于用什么概念组织论文。

## 题目（暂）

Consistency Testing of Python-Driven Compilers along the Compilation Path

## 问题

编译器测试的传统对象是"程序"：生成或变异程序，把编译结果与参考执行比较。这一设定隐含一个假设——对同一程序，编译器只有一条路径。对 `torch.compile` 这个假设不成立。同一段源码在运行时会走不同的路径：Dynamo 在哪些语句处中断并生成恢复函数，取决于调用现场；AOTAutograd 是否参与，取决于是否需要梯度；Inductor 生成的是标量还是向量循环，取决于张量长度；一个算子走专门 lowering 还是分解，取决于 dtype；代码在 TorchDispatchMode、autocast、reduce-overhead 下运行时，参与的组件又不同；导出与 AOTI 打包再加载，则换成另一套运行时。用户看到的是同一份源码，编译器执行的是这些路径之一。一致性失效大多发生在程序很少触及的语义与流水线很少走到的路径的交点。只在程序轴上取样的方法到不了这些交点，也说不出差异是哪一层引入的。

## 观察

编译路径是可以枚举并逐个控制的。可以插入 graph break 的语句位置、可以选择的后端与模式、可以切换的执行上下文、可以往返的制品格式，都是流水线暴露出来的开关，数量有限、语义明确，且每一个开关在规范上都不改变程序的结果。同样，程序侧能改变编译行为的因子也可以从源码与算子元数据中枚举。把两组因子都当作测试维度，固定一组、在另一组上一次改一个，得到的每个差异都有唯一的候选原因。

## 方法

1. 因子模型。一次编译执行由 (程序, 输入, 路径) 三元组决定。程序侧因子来自源码静态分析（形状、dtype、stride、requires_grad、Python 标量、全局状态）和算子元数据（dtype 支持表、样本形状、边界值）。路径侧因子来自流水线结构：graph break 位置、后端层（Dynamo-only、aot_eager、inductor）、执行上下文（dispatch mode、autocast、dynamic、cudagraphs）、制品路径（export 保存与加载、AOTI 打包、runner 生命周期）。
2. 一次变一个因子的执行矩阵。以 eager 为参照，每个测试只改动一个因子；同一程序在不同路径上的差异因此可以直接归因到该因子对应的组件。
3. Oracle。七类可观察量：数值（float64 或多精度参照）、dtype 与形状与 stride、对象身份与别名、异常类型及其是否被同一 handler 接住、副作用与外部状态、进程级结果。只比输出值的 oracle 看不到其中五类。
4. 归因。分层执行给出差异首次出现的层；根因不在流水线内（eager 内核、fx 层、C++ 编译器）的发现单列。

## 创新点

1. 把编译路径提升为一致性测试的一个维度，并给出可枚举、可逐个控制的路径因子集合。以往方法把路径当作固定黑箱。
2. 一个由程序侧与路径侧因子构成的执行矩阵，配合覆盖七类可观察量的 oracle：矩阵保证差异可归因，oracle 保证副作用、身份、异常处理与进程级失效不被漏掉。
3. 在 PyTorch 2.14 与 nightly 上的两轮报告共 73 项，按四档口径为已修复 14、已确认 10、Pending 48、拒绝 1；根因按流水线内、流水线外、跨目标三类分开统计，并给出负结果。

## 证据的组织（评估）

- RQ1 路径轴的边际贡献。同一 274 个程序、同一 oracle：三轮只改程序的差分只出已知分歧；在路径轴上加一个因子（graph break 位置）一轮出两条新缺陷；按机制补 33 个程序再出一条。
- RQ2 程序轴的边际贡献。固定路径，只加元数据驱动的边界值与 dtype 因子：一轮 134 个算子 / 418 对，CUDA 上再加 73 对。
- RQ3 oracle 的贡献。逐类去掉可观察量，统计漏掉的发现；每类给一个代表（erf 精度、`x * 1` 返回输入本身、IndexError 逃逸、`move_to_end` 丢失、Windows AOTI 崩溃）。
- RQ4 归因。分层定位到单一层的比例；与已修复项的实际修复位置对照。
- RQ5 与现有生成器对照。注入缺陷基准上 Random / NNSmith 的比较；结论是程序轴生成器在路径轴上的覆盖为零。
- RQ6 真实缺陷。73 项的分类、四档反应、负结果表。

## 与相关工作的关系

程序生成（NNSmith、NeuRI、HirGen）、API 调用生成（FreeFuzz、DeepREL、TitanFuzz）、IR 变异（Tzer、MLIRSmith）、语义保持的程序变换（TorchProbe）、冷热缓存比较（AlignGuard）都在程序或输入维度上工作；差分测试与等价修改（EMI）提供 oracle 思路。本文与它们的区别是测试维度，而不是 oracle。

## 方案 A 与 B 的取舍

- A（蜕变测试框架）：概念上更整洁，能把 TorchProbe、EMI、AlignGuard 统一进同一框架下比较，评审容易定位到已知的方法论谱系；风险是被认为"只是把差分测试改名"。
- B（编译路径作为测试维度）：论点更直接，主张"路径是被忽视的维度"，创新点不依赖框架的命名；风险是 oracle 部分显得像工程细节，需要靠 RQ3 撑住。
- 折中：以 B 为主线，方法节用一段说明每个路径因子在形式上是一个语义保持变换、oracle 是一致性关系，把蜕变测试作为解释而不是框架。
