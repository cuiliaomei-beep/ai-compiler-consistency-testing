torch.compile 缺陷研究讲解

这份说明假设你不懂 Python、也不懂编译器。它从"这件事到底在研究什么"讲起，接着讲计划怎么定、实际怎么做、怎么保证找到的问题是真的，最后把 27 条 issue 逐条用大白话解释：出了什么错、打个比方像什么、为什么值得报告。

1背景：研究的是什么

PyTorch 是全世界用得最多的深度学习软件之一。研究者用 Python 写几行代码描述一个神经网络，PyTorch 负责真正去做海量的数字计算（矩阵乘法、求和、求导等）。

PyTorch 有两种运行方式：

  • 普通模式（叫 eager）：代码写一行、执行一行，每一步都立刻算出结果。简单、可靠，但慢。
  • 编译模式（叫 torch.compile）：先把整段代码"读懂"，整体优化，生成专门的机器代码再运行。通常快很多，所以大公司训练大模型都会打开它。
打个比方：普通模式像同声传译，说一句翻一句；编译模式像先把整篇演讲稿拿去精译、排版、印刷成册再发给听众。印刷版读起来快，但如果精译时译错了一个词，所有听众拿到的都是错的，而且谁也不会注意到——因为印刷版看起来非常正式。

核心原则：编译只应该让程序变快，不应该改变结果。同样的输入，eager 算出来是 3.14，编译后也必须是 3.14。

你的论文（ICSE 2027 在审的 paper749）研究的是"有毒编译"：编译悄悄改变了程序的行为。这次会话做的是论文的后续工作——做一个自动工具，系统地去找 torch.compile 和 eager 结果不一致的地方，找到后整理成规范的 bug 报告（issue）交给 PyTorch 官方修复。每一条被确认的 issue，都是这个检测方法有效的实证。

编译器内部分几层（理解每条 issue "错在哪一层"要用到）

torch.compile 不是一个整体，而是一条流水线，每一层都可能出错：

  • Dynamo：读 Python 代码，把其中的数学计算"抄"成一张计算图。它必须理解 Python 的各种语法细节（随机数、字符串、异常……），这里出错属于"读错了代码"。
  • AOTAutograd：训练模型需要"求导"（算梯度，告诉模型往哪个方向改）。这一层提前把求导步骤也推出来。这里出错就是"导数算错"。
  • Inductor：把计算图翻译成真正的 C++ 代码（CPU 用）或 Triton 代码（GPU 用），再交给编译器变成机器码。这里出错属于"翻译成机器语言时译错"。
  • 分解（decomposition）：Inductor 会把复杂运算拆成简单运算再生成代码，就像把"求平均"拆成"先求和、再除以个数"。拆法和原版不完全等价时就会出错。
  • meta / FakeTensor：编译前先"空跑"一遍，只推算形状和类型、不做真实计算，用来提前规划内存。空跑的规则和真实计算不一致也会出错。

2几个必须懂的词

张量（tensor）一大块排成表格的数字。一张图片就是一个"高×宽×颜色通道"的张量。
算子（operator）对张量做的一种运算，比如加法、求平均、求逆矩阵。PyTorch 有上千个。
精度 / dtype每个数字用多少位存。float64 很精确；float32 常用；float16 / bfloat16 省内存但精度低。类型搞错会导致精度丢失或内存浪费。
复数（complex）带虚部的数，信号处理、量子物理里常用。复数的求导规则比实数更复杂，容易写错。
梯度 / 反向传播训练时告诉每个参数"往哪边改、改多少"的数字。梯度错了，模型会朝错误方向学，而且不报错。
前向模式求导（jvp）另一种求导方式，科学计算里常用。和普通的反向传播走不同的代码路径。
动态形状（dynamic=True）编译时不把"数组有多大"写死，好让同一份编译结果能处理不同大小的输入。代码里会出现 s0、ks1 这样的符号代替具体数字。
NaN / infNaN 是"不是一个数"（比如 0/0 的结果），inf 是无穷大。它们一旦出现，后面的计算基本都坏了。
INTERNAL ASSERTPyTorch 内部的自检失败，报错信息里写着"请向 PyTorch 报告 bug"。它本身就说明是框架的错，不是用户的错。
进程崩溃程序直接消失，没有任何错误提示（Windows 显示 0xC0000005，Linux 显示 SIGSEGV）。比报错更糟，因为很难知道原因。
nightlyPyTorch 每天自动发布的最新开发版。在 nightly 上还能复现，说明官方还没修。
issue在 GitHub 上给项目提交的问题报告。PyTorch 的 issue 有固定模板：问题描述、错误日志、版本信息。

3计划

起点是研究计划文档 Toxic_Compilation_Consistency_Detection_Research_Plan_Updated.md，核心思想叫差分测试：

打个比方：不知道标准答案时，就让几个人独立做同一道题，再对答案。如果大家答案都一样，大概率是对的；如果有人答得不一样，就重点检查他。这里"几个人"就是同一个程序的不同运行方式。

计划规定了几种"做题的人"，从最简单到最复杂：

代号运行方式作用
E0 eager不编译，直接算基准答案
E1 backend=eager只经过 Dynamo，不做后面的优化若这里就错，是 Dynamo 读错了代码
E2 aot_eager经过 Dynamo + AOTAutograd若 E1 对 E2 错，是求导那层的问题
E3 inductor（CPU）完整编译，生成 C++若 E2 对 E3 错，是生成代码那层的问题
E4 inductor（GPU）完整编译，生成 GPU 代码GPU 特有的问题

逐层对比的好处是：不仅知道"错了"，还能指出"错在哪一层"，这对维护者修 bug 非常有用。计划还定义了几种判断"不一致"的标准（结果数值、形状、数据类型、是否报错、是否崩溃等），以及找到后怎么缩小复现代码、查重、写报告。

5怎么保证不是误报

每条 issue 在写进目录之前都过了下面几道关：

  1. 有"标准答案"。数值类问题用更高精度（float64 或 complex128）重新算一遍当真值，看到底是 eager 对还是编译后对。这样避免把"两边都有正常的舍入误差"误当成 bug。
  2. 逐层定位。同一段代码在 E1/E2/E3 各跑一遍，确认错在哪一层，报告里写清楚。
  3. 缩到最小。把触发问题的代码缩到几行，任何人复制粘贴就能看到。
  4. 跨环境、跨版本。Windows 与 Linux、正式版 2.14.0 与 nightly 都跑过；GPU 相关的在 Kaggle 的 T4 显卡上跑。
  5. 查重。每条用多组关键词搜 PyTorch 的 issue 和修复记录。发现已有人报过的就不再报（最终排除了 2 条）。
  6. 独立复核。9 月 15 日把 27 条的复现代码重新写一遍，每条在全新的进程里跑，避免前一个测试残留的状态影响后一个。结果 25 条重现、1 条需要 GPU（引用 Kaggle 结果）。
复核时发现并改正的两处：
① 第 07 条：之前表格里有几格写着"正常"，其实是同一个程序里前面的测试留下的状态让后面的测试侥幸通过；改成每格单独运行后，全部是出错。问题比原来写的更严重，已改正并在报告里提醒维护者。
② 第 13 条：原来写"导出时静默丢掉了更新"，单独验证后发现不对——导出后的模型其实照常更新了。这句话删掉，报告只保留确实成立的两点。
这正是复核的意义：把不准确的地方在提交前找出来。

627 条 issue 逐条讲解

编号就是建议提交顺序。高 表示算错了却不报错、或者程序直接崩溃；中 表示编译失败或内部自检报错；低 表示只在很少见的用法下出现。"层"指错在第 1 节图里的哪一层。

01复数的伪逆矩阵，编译后梯度算错高AOTAutograd已提交 #197084
发生了什么
torch.linalg.pinv（伪逆矩阵，线性代数常用运算）和 matrix_sqrth（矩阵平方根）作用在复数上时，编译后算出的梯度是错的，误差高达 17（正确值只在 1 左右），而且完全不报错。实数输入没问题。
打个比方
导航软件在普通模式下指路正确，切到"加速模式"后，只要走的是某一类路（复数），就会把"向东"说成"向西"，语气还一样肯定。
为什么要紧
梯度决定模型怎么学。梯度错了，训练会朝错误方向走，用户很可能只觉得"模型效果差"，根本想不到是框架算错。PyTorch 专门有"静默正确性错误"这个最高关注类别，机器人已经给它打上了。
怎么确认的
用 gradcheck（PyTorch 官方的梯度检查工具）验证：普通模式通过、编译后不通过。只经过 Dynamo 是对的，一经过 AOTAutograd 就错，所以定位到 AOTAutograd。扫描了所有支持复数求导的算子，只有这两个有问题。
02编译后"随机打乱"每次都打成同一个顺序高Dynamo
发生了什么
Python 自带的 random.shuffle（随机打乱列表）和 random.sample（随机抽样），放进编译后的函数里，第一次调用是随机的，之后每一次都返回和第一次一模一样的结果。
打个比方
请人每天给你随机抽一张扑克牌，结果他第一天抽完就把那张牌拍照了，之后每天给你看同一张照片。
为什么要紧
训练中常用随机打乱数据、随机抽样。被"冻结"后训练就不再随机，效果变差且毫无提示。
怎么确认的
在 Dynamo 源码里找到原因：它在"读代码"时就把打乱结果算好当成固定值写死了，而同类的 random.random 等函数是每次运行时重新算的。Windows、Linux、正式版和 nightly 都复现。
03对 ldexp 做前向求导并编译，程序直接崩溃高AOTAutograd
发生了什么
torch.ldexp(x, e) 计算 x×2e。用前向模式求导（jvp）并以 aot_eager 方式编译时，程序没有任何报错直接消失（Windows 内存访问违规、Linux 段错误）。
打个比方
不是算错，而是计算器直接黑屏关机，也不告诉你为什么。
为什么要紧
进程崩溃是最难排查的一类问题：没有错误信息、没有出错位置。一次跑几个小时的任务会整个丢失。
怎么确认的
每种情况放在单独的进程里跑并记录退出码：普通模式、只 Dynamo、完整编译都正常，唯独 aot_eager 崩溃。在 507 个支持前向求导的算子里只有它会让进程消失。
04生成的 C++ 代码里混进了 Python 语法，编译失败高Inductor（CPU）
发生了什么
在动态形状下对某种形状的数据求最小值位置（argmin），Inductor 生成的 C++ 代码里出现了 ks1**2。** 是 Python 的"乘方"写法，C++ 不认识，于是 C++ 编译器报错。
打个比方
把中文稿翻成英文时，中间夹了一句没翻译的中文，英文读者读到那里就卡住了。
为什么要紧
只在两个维度大小恰好相同时出现，形状稍微一变又好了，用户会觉得"时好时坏"。
怎么确认的
在源码 cpp.py 里找到两处用了 Python 的打印函数而不是 C++ 的打印函数，是两行代码的疏漏。Windows（MSVC 编译器）和 Linux（GCC 编译器）都失败，GPU 版正常。
05要求放在 CPU 上的数据，被放到了显卡上高Inductor（GPU 加速模式）
发生了什么
在 GPU 上打开 cudagraphs（一种常用的加速模式，mode="reduce-overhead" 默认打开），代码明确写 device="cpu" 创建数据，编译后却返回了一个在显卡上的张量。
打个比方
你让快递寄到家里，快递员却自作主张寄到了公司。
为什么要紧
后续代码会因为"数据不在同一个设备上"而报错，但报错位置离真正出问题的那一行很远，很难查。
怎么确认的
在 Kaggle 的 Tesla T4 显卡上，PyTorch 2.10 和 2.14 都复现；不开 cudagraphs 时正常。
06算方差/标准差时，编译后精度下降高Inductor（CPU）
发生了什么
CPU 上普通模式计算方差时用高精度（double）累加，编译后改用低精度（float32）累加。结果：非常小的数（1e-30 量级）方差变成 0、梯度全变 0；非常大的数（1e30）变成无穷大；更常见的情况——数据都在 10 万左右时，方差误差从千万分之五变成千分之三。
打个比方
用精度到毫米的尺子和精度到厘米的尺子量头发丝的粗细差异，厘米尺会告诉你"没有差异"。
为什么要紧
梯度变成 0 意味着训练悄悄停止；统计值偏差会影响归一化等后续步骤。都不报错。
怎么确认的
和 float64 真值对比，普通模式误差很小、编译后误差大几个数量级；在 PyTorch 已有 issue 里找到同根因的 LayerNorm 例子（只修了那一处）。
07在编译里做前向求导，分位数等运算触发内部自检失败中Dynamo
发生了什么
对 quantile（分位数，比如中位数）、nanquantile、addr 做前向求导并编译，报 INTERNAL ASSERT（"请向 PyTorch 报告 bug"）。三种编译方式都失败，普通模式正常。
打个比方
机器自检时发现"不该出现的状态"，直接停机并亮红灯。
为什么要紧
没有任何绕过办法（所有编译方式都失败），而且报错本身就说明是框架内部问题。
怎么确认的
复核时发现：多个测试连着在同一程序里跑时，后面的偶尔会侥幸通过。改为每个单独运行后全部失败，报告里专门提醒了维护者这一点。
08ldexp 编译后结果的数字类型变了中Inductor
发生了什么
普通模式下，两个输入的类型会按规则"就高"合并（比如半精度×单精度→单精度）。编译后规则变了：有时类型变高、有时变低，只看第一个输入。
打个比方
两个人合伙，规定"按出钱多的那个人的意见"，编译后却变成"永远听先开口的那个人"。
为什么要紧
类型变低会丢精度，变高会多占内存，后面代码可能因类型不符报错。
怎么确认的
只经过 AOTAutograd 的版本和普通模式一致，只有 Inductor 不同；找到了今年 1 月引入这个问题的改动（PR #171721）。CPU 和 GPU 都复现。
09打开 compiled autograd 后，图像插值的求导报内部错误中compiled autograd
发生了什么
F.interpolate（图像缩放）用双线性、双三次等方式时，打开"连求导也编译"的选项，求导阶段报 INTERNAL ASSERT。最近邻方式正常。
打个比方
把参数装进信封时把顺序装错了，收件人拆开发现"应该是一串数字的地方放的是一个开关"。
为什么要紧
图像缩放是分割、超分辨率等模型的常规组件，打开这个优化选项就无法训练。
怎么确认的
对所有支持求导的算子开这个选项扫描，只有插值这一族失败。Windows、Linux、正式版、nightly 都复现。
10动态形状下，格式化字符串让编译器内部出错中Dynamo
发生了什么
代码里写 f"{x.shape[0]:d}"（把数组大小按整数格式写进字符串，常用于打印日志），动态形状下编译器报内部错误：它把"数组大小"当成了文字去套整数格式。
打个比方
表格要求填"年龄（数字）"，系统却把"年龄"两个字本身填了进去，然后说格式不对。
为什么要紧
打印日志、写报错信息是再普通不过的写法；用户自己的报错信息反而被替换成框架的内部错误。
怎么确认的
不用格式说明符、或关闭动态形状都正常。两个操作系统、两个版本复现。
11编译优化器时，复数参数 + 默认实现报错中Inductor
发生了什么
把 SGD 优化器的更新步骤编译起来，参数是复数、使用默认的"批量更新"实现时，Inductor 报断言错误。Adam 等其他优化器正常。
打个比方
五家店都能处理外币付款，只有一家店的收银机遇到外币就卡死。
为什么要紧
编译优化器步骤是官方推荐的提速手段，复数参数的用户会直接失败。
怎么确认的
扫描了 11 种优化器、各种选项和参数类型（1584 种组合），只有这一种失败。查到一个未合并的旧修复尝试（PR #178192）处理过同一个断言。
12空数据做图像缩放，编译后读到了越界内存，返回一堆 NaN中Inductor
发生了什么
宽度为 0 的数据做 F.interpolate，普通模式会正确报错"尺寸必须大于 0"，编译后却返回一个 2×3×3 全是 NaN 的结果——生成的代码去读一块根本不存在的数据。
打个比方
让人从空盒子里数苹果，正常人说"盒子是空的"，他却伸手到盒子外面摸出一些不知道是什么的东西报数。
为什么要紧
偶尔出现空批次的流水线，会把 NaN 悄悄传下去；在 GPU 上同样的越界读取可能直接非法访问内存。
怎么确认的
CPU 和 GPU 都复现；和已有的"编译缺少输入检查"类 issue 同族但不重复。
13导出部署时，同一个模型在三个步骤里得到三种不同对待中export / AOTInductor
发生了什么
模型里的统计量（running mean）不是登记在模型里，而是直接引用外面的一个张量并原地更新。导出（export）顺利通过、运行正常；下一步"分解"时报错说"这种写法不允许"；再下一步"打包"时报 INTERNAL ASSERT。
打个比方
办证时第一个窗口说"材料齐全"，第二个窗口说"材料不合规"，第三个窗口直接系统崩溃。
为什么要紧
用户在第一步得到"没问题"的信号，到部署最后一步才撞墙，还被要求去报 bug。
怎么确认的
复核时发现原稿"导出时丢掉更新"的说法不成立，已删除；保留的两点在两个系统、两个版本都复现。
14求向量范数时，维度写成 -1 就编译失败，写成 1 就正常中分解（_refs）
发生了什么
对 0 行 5 列的数据求每行的最大绝对值，普通模式返回空结果；编译时写 dim=-1（倒数第一个维度）报错说"这个维度是空的"，而写 dim=1（同一个维度）却正常。
打个比方
问"最后一排有人吗"系统说没人，问"第二排有人吗"（其实就是最后一排）系统说有人。
为什么要紧
负数下标是非常常见的写法；报错信息还指错了维度，误导用户。
怎么确认的
定位到源码一行检查只处理了正数下标，没把负数换算过来。
15两个损失函数在半精度训练时，编译后结果类型变成单精度中Inductor（CPU）
发生了什么
binary_cross_entropy（带权重）和 huber_loss 输入是半精度时，普通模式返回半精度，编译后返回单精度。其他几个同类损失函数没问题。
打个比方
全班都交 A4 纸作业，只有两个同学编译后交成了 A3。
为什么要紧
半精度训练本来是为了省内存，结果类型被悄悄改变，后续可能报错或多占内存。
怎么确认的
只经过 AOTAutograd 的版本和普通模式一致；PyTorch 以前修过这个函数的另一个变体（with_logits），这个没修到。
16空数据求距离的导数，普通模式就会让程序崩溃中普通模式本身
发生了什么
F.pdist（两两之间的距离）输入 0 行时，前向返回空结果，但求导时程序直接崩溃（Windows 报整数除以零，Linux 段错误）。这条不是编译的问题，是普通模式本身的缺陷，所以用普通 bug 模板。
打个比方
计算"平均每人分几个苹果"时，人数是 0，计算器没有检查就去除，直接死机。
为什么要紧
批次偶尔为空时整个进程丢失，没有报错信息；编译模式也调用同一段代码，同样崩溃。
怎么确认的
在子进程里跑，1 行、2 行都正常，只有 0 行崩溃；GPU 版本正常。
17编译函数里设置随机种子，第一次调用不生效中Dynamo
发生了什么
在函数里写 random.seed(0) 后取随机数，普通模式每次都得到同样的数；编译后第一次调用得到别的数，从第二次开始才正确。
打个比方
闹钟设好了时间，但只有第一天不响，之后每天都准。
为什么要紧
设置种子就是为了结果可复现；只有第一次不一致，很容易被误以为是偶发的不稳定。
怎么确认的
和第 02 条同一段源码，但症状不同，单独报告。
18Python 3.14 + 动态形状下，比较两个"具名元组"导致无限递归中Dynamo
发生了什么
比较两个装着张量的 namedtuple 是否相等，普通模式正常返回；编译（动态形状、Python 3.14）后栈溢出崩溃。Python 3.11 正常。
打个比方
两面镜子对着照，影像无限套下去，最后系统放弃。
为什么要紧
只在新版 Python 上出现，随着用户升级 Python 会越来越多人碰到。
怎么确认的
在 Windows Python 3.14 复现，Linux Python 3.11 不复现，报告里明确写了是 3.14 专属。
19Windows 上开最大自动调优，批量矩阵乘法必然失败中Inductor（Windows）
发生了什么
Windows 上打开 max_autotune，torch.bmm（批量矩阵乘法）编译失败，提示找不到某个函数。普通矩阵乘法正常，Linux 正常。
打个比方
店里新到的商品忘了贴价签，收银员扫不到就无法结账。
为什么要紧
矩阵乘法是最核心的运算之一，Windows 用户开这个选项就用不了。
怎么确认的
找到原因：批量乘法的代码模板少了 Windows 需要的"导出声明"，而同类模板都有，一行就能修。
20打包部署时，不支持返回"带名字的结果"低AOTInductor
发生了什么
torch.max(x, dim)、topk 等返回"值 + 位置"的带名字结果。普通运行和编译都没问题，打包部署时报错说不会保存这种类型。
打个比方
快递公司能送普通包裹，但不接受"贴了标签的包裹"，拆掉标签就能寄。
为什么要紧
报错指向一个用户无法操作的内部函数；在所有打包失败的算子里 35 个中有 33 个是这个原因。
怎么确认的
查到一个 2023 年起就挂着未合并的相关修复（PR #113258）。
21布尔值做线性插值，普通模式可以、编译失败低Inductor
发生了什么
torch.lerp（在两个值之间按比例取中间值）的两端是真/假值、比例是小数时，普通模式先转成小数再算，编译时先做"真减假"再转换，布尔值不能相减，报错。
打个比方
先换算单位再加减就没事，编译后变成先加减再换算，于是"米减秒"算不下去。
为什么要紧
用法少见，但属于普通模式接受、编译拒绝的不一致。
怎么确认的
整数输入正常，只经过 AOTAutograd 也正常，CPU 和 GPU 都复现。
22求和/求积时指定结果为真假值，编译失败低Inductor（CPU）
发生了什么
torch.sum(半精度数据, dtype=bool) 生成的 C++ 编译不过；torch.prod(..., dtype=bool) 触发断言。普通模式返回一个真假值。
打个比方
模板库里没有"用是/否来累加"这种表格，只能报错。
为什么要紧
少见，但普通模式支持、编译不支持；单精度输入却又能过，行为不统一。
怎么确认的
Windows 和 Linux 两种 C++ 编译器都失败。
23偏置是单个数时，开最大自动调优后矩阵运算编译失败低Inductor
发生了什么
torch.addmm(偏置, x, y) 的偏置是一个单独的数时，默认编译正常，打开 max_autotune 后报"下标越界"。
打个比方
程序默认"偏置至少是一行数"，直接去取第一格，没料到它只是一个数。
为什么要紧
报错看不出原因；已有一个针对相邻情况的修复（PR #185578），但没覆盖这种情况。
怎么确认的
CPU、GPU 都复现，定位到源码里"先取下标、后检查维度"的顺序问题。
24空数据求平均，编译后返回 0 而不是 NaN低Inductor
发生了什么
torch.var_mean 对空数据，普通模式平均值是 NaN（没有数据就没有平均值），编译后是 0。
打个比方
一个人都没来考试，平均分本应是"无法计算"，却被登记成了 0 分。
为什么要紧
0 看起来像个正常数，会掩盖"输入是空的"这一事实。
怎么确认的
各种精度、形状、选项组合都复现，CPU 和 GPU 都有。
25通道重排后，编译结果丢失了数据的内存排列方式低Inductor
发生了什么
图像数据有两种内存排列方式（按通道分块，或按像素把通道挨着放，后者叫 channels_last，卷积更快）。channel_shuffle 在普通模式下保持 channels_last，编译后变回了另一种。
打个比方
书按"作者"排好了架，整理一遍后又被按"出版年份"排了回去，书没丢，但找起来慢了。
为什么要紧
数值不错，但后续卷积可能多一次复制、变慢。PyTorch 已经修过好几个同类问题。
怎么确认的
对比输出的内存步长，普通模式与只 AOTAutograd 的版本一致，Inductor 不同。
26编译后，"键不存在"错误的文字少了引号低Dynamo
发生了什么
Python 里 str(KeyError("k")) 的结果是带引号的 'k'；编译后变成不带引号的 k。
打个比方
抄写别人的话时漏掉了引号，意思没变，但严格对照原文时对不上。
为什么要紧
影响小，但如果代码按错误文字做判断或写日志，结果会不同。说明 Dynamo 模拟 Python 行为不完全。
怎么确认的
其他异常类型正常，只有 KeyError 这个特例（它的文字规则本来就特殊）。
27复数取绝对值写入另一种精度的结果变量，编译拒绝低meta（空跑检查）
发生了什么
torch.abs(复数, out=双精度变量)：普通模式把结果转换后写进去；编译时的"空跑检查"要求类型必须完全一致，于是拒绝。同类的 torch.angle 两边都允许。
打个比方
前台登记处比实际办事窗口要求更严，窗口能办的事，登记处先不让进。
为什么要紧
用法少见。维护者也可能认为应该让普通模式也拒绝，所以放在最后。
怎么确认的
两个系统、两个版本都复现，查重无同报告。

7没发现问题的方向

研究里"没找到问题"同样有价值，它说明那部分实现得可靠，也避免以后重复白费功夫。下面这些方向都系统地试过，结果一致：

  • 20 种冷门编译选项，覆盖 593 个单算子和 68 个多算子程序，共一万多次编译，没有一处结果不同。
  • 编译结果重复使用时改变运行环境（精度设置、训练/推理模式、线程数等 20 种）、以及输入大小变成 0 或 1。
  • 跨进程的编译缓存、真实的图像识别模型（CPU 与 GPU）、参数"以何种写法传进来"。
  • 批处理变换（vmap）经过编译：678 个算子无分歧。
  • 二阶导数：PyTorch 明确说明编译不支持，所以不算缺陷。
